# AI-помощник для карточек товара

Сервис берёт данные о приборе (JSON) и делает черновик карточки товара для интернет-магазина: заголовок, SEO-описание, характеристики, запросы для поиска, блок «кому подходит».

---

## Как запустить

### Шаг 1. Окружение

Нужен Python 3.11+ и `uv` (или обычный `venv` + `pip`).

```bash
cd test
uv venv
uv pip install -r requirements.txt
```

### Шаг 2. Ключ от LLM

```bash
cp .env.example .env
```

Откройте `.env` и впишите адрес API, ключ и модель (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`). Подходит любой OpenAI-совместимый сервис - OpenAI, OpenRouter, DeepSeek, локальная Ollama и т.д. Ключ остаётся только в `.env`, в код не попадает.

> Без ключа сервис не запустится и честно скажет об этом. Это осознанно: прототип работает с реальной LLM, а не подделывает ответы.

### Шаг 3. Запуск

Один товар (просто укажите путь к JSON-файлу):

```bash
uv run python app/main.py products/testo-510.json --format md    # Markdown
uv run python app/main.py products/testo-510.json --format json  # JSON
uv run python app/main.py products/testo-510.json --format txt   # текст
```

Сразу несколько товаров (все JSON из папки, в несколько потоков):

```bash
uv run python app/main.py products/ --batch --workers 4 --format md --out-dir products/out
```

Или как сервис с веб-формой:

```bash
uv run uvicorn app.main:app
```

Откройте http://localhost:8000/docs - там удобная форма: вставляете JSON, нажимаете Execute и получаете карточку.

Тесты:

```bash
uv run pytest tests/ -q     # 41 passed
```

Тесты работают без ключа и сети - LLM там подменяется тестовой заглушкой.

### Формат входных данных

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0-1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Все поля необязательные. `specs` может быть объектом с названиями характеристик или просто текстом.

## Что получается на выходе

### Пример 1. Манометр DM 02

Вход - как выше. Выход (сокращённо):

```
# Манометр показывающий DM 02 Манотомь 0-1,6 МПа G1/2

Ищете надежное оборудование для измерения давления? Предлагаем купить манометр
показывающий dm 02 от производителя «Манотомь». Диапазон измерений - от 0 до 1,6 МПа,
класс точности 1,5. Для интеграции в системы предусмотрено присоединение G1/2,
диаметр корпуса 100 мм для удобного считывания показаний. ...

Характеристики:
- диапазон измерений: 0-1,6 МПа
- класс точности: 1,5
- присоединение: G1/2
- диаметр корпуса: 100 мм

Поисковые запросы:
- манометр показывающий dm 02 купить
- купить манометр показывающий dm 02
- манотомь манометр показывающий dm 02
- манотомь приборы купить

Кому подходит: промышленные предприятия, монтажные организации, специалисты
по обслуживанию инженерных систем - для измерения избыточного давления.
```

Вход - кусок каталога с вариантами исполнения:

```json
  "specs": {
    "модификации": [
      { "код товара": "87780", "тип корпуса": "Н-настенный, 129×110×69 мм, IP66",
        "тип входа": "У2-Универсальные измерительные входы",
        "тип выхода 1": "Р-электромагнитное реле 8 А 220 В", "цена с НДС": "6 864 ₽" },
      { "код товара": "125242", "тип корпуса": "Щ2-щитовой, 96х48х100 мм, IP54",
        "тип входа": "У2-Универсальные измерительные входы", "цена с НДС": "6 628 ₽" }
    ]
  }
}
```

Выход (сокращённо):

```
# Регулятор ОВЕН 2ТРМ1 - купить измеритель-регулятор

Регулятор 2ТРМ1 с универсальными входами (У2) и двумя реле (8 А 220 В).

(IP54), с интерфейсом RS-485 и без. ...

Характеристики:
- модификация 87780: код 87780; Н-настенный, 129×110×69 мм, IP66;
  входы У2; реле 8 А 220 В [цена с НДС: 6 864 ₽]
- модификация 125242: код 125242; Щ2-щитовой, 96х48х100 мм, IP54; ...

Кому подходит: промышленные предприятия и системы автоматизации -
для измерения и двухканального регулирования температуры и других параметров.
```

Полные версии (с предупреждениями и списком недостающих данных) лежат в `examples/` и `products/out/`.

## Как это работает и почему так сделано

Пайплайн: `вход → извлечение фактов → генерация → проверка → выход`

### Извлечение фактов

Из входных данных вытаскиваются все характеристики. Каждая запоминает свой источник (`specs` / `description` / расшифровано по коду). Если `specs` пришёл текстом - LLM разбирает его на факты, ничего не додумывая.

### Генерация

Второй промпт пишет карточку **только по этим фактам**. Модели не передаётся ничего, кроме извлечённых данных, поэтому выдумать характеристику она просто не может.

> **Почему это главное**: в ТЗ трижды повторяется «не выдумывайте характеристики». Мы решили это не «пожалуйста, не выдумывай» в промпте, а на уровне архитектуры - модель физически не имеет данных, из которых можно что-то придумать.

Коды модификаций (вроде `2ТРМ1-Н.У2.РР.RS`) проходят через систему без изменений - вымышленный код означал бы несуществующий товар.

Запросы для поиска собираются из названия и характеристик по шаблонам (без LLM - чтобы были стабильными).

### Проверка

- Заголовок не длиннее 70 символов, описание - 800-1200 (проверяется кодом, а не «на глаз»)
- Каждая характеристика из входа гарантированно попадает в вывод
- Цены и «в наличии» не попадают в характеристики
- Если данные противоречат друг другу (в specs 0-20 м, в описании 0-10 м) - система это показывает, а не исправляет молча

Полные формулировки промптов - в коде (`app/pipeline.py`).

## Что сейчас не идеально

- **Текст зависит от модели.** Сервис не подменяет LLM шаблонами: какая модель, такой и язык. Если API недоступен - вернётся каркас из характеристик с предупреждением, но без выдумки.
- **Один клиент для всех** - OpenAI-совместимый интерфейс. Остальные провайдеры подключаются через него же, но без их фирменных особенностей structured output.
- **Расшифровка названия по коду** срабатывает, только если в данных есть расшифровки соседних вариантов. Нет расшифровок - честно пишем «данных нет».
- **Поиск противоречий** ловит числовые расхождения. Сильно перефразированное описание может не распознаться.
- **Разбор описания** покрывает частые формулировки (диапазон, температура, погрешность, материал), но это не полноценный NLP-парсер.

## Чего не сделано (но хочется)

- **Запросы через Wordstat** - реальные частотности вместо шаблонов. Упирается в токен Яндекс.Директа, поэтому пока не сделано.
- **Сильнее многопоточность** - асинхронный клиент, очереди, прогресс-бар и отчёт по пачке, чтобы обрабатывать весь каталог быстрее.
- Векторный поиск по техпаспортам - чтобы характеристики заполнялись сами из больших документов.
- CI: тесты и проверки на каждый PR, версионирование промптов.
- Адаптация вывода под формат загрузки конкретного магазина.

## Структура проекта

```
app/
  main.py        - запуск (команда + сервис)
  config.py      - настройки (.env)
  models.py      - типы входных/выходных данных
  providers.py   - клиент LLM + ограничитель запросов
  pipeline.py    - основная логика: факты → карточка → проверка
fixtures/        - 7 тестовых входов на разные случаи
products/        - 3 реальных товара из каталога
examples/        - готовые карточки по тестовым входам
tests/           - 41 проверка
```
